# Lobby Discord Bot

Discord-бот, работающий на нескольких серверах/каналах. Основной функционал заточен
под игру Social Deduction Game (управление игровыми серверами, ELO-рейтинг, статистика матчей,
мониторинг лобби), но часть функций общая и не привязана к игре: например, оповещения о Twitch-стримах.

Этот файл: принципы и правила для любой правки. Устройство кода (фичи, задачи, события) в
`docs/ARCHITECTURE.md`.

## Принципы
Обязательны для любой правки, размер задачи меняет объём работы, но не планку.
- **Сначала найди владельца.** У каждого факта одно место: настройки в `Settings`, коллекции в `db.py`,
  сезон в `current_season()`, права в `lobby_bot/shared/permissions.py`, правила фичи в её `service.py`.
  Прочитай владельца до того, как писать вызывающий код; если его не хватает, расширь его, а не пиши рядом своё.
- **Одно правило, одна реализация.** Нужна логика другой фичи: вызови её `service` или подпишись на событие,
  не копируй. Встретил одно правило в двух местах: оставь у владельца, вызывающих переведи, копию удали.
- **Меньше кода.** Удаление лучше абстракции. Не добавлять параметры, обёртки и «задел на будущее»,
  которыми ничего не пользуется. Мёртвый код удалять.
- **Чинить причину, а не симптом.** Не глушить исключение, не ослаблять и не пропускать тест, не обходить
  ошибку в вызывающем коде. Зелёный `pytest` не оправдывает костыль.
- **Долг не копировать.** Встреченную проблему исправить у владельца или, если это выходит за рамки задачи,
  явно назвать в ответе и в «Известных проблемах». Не строить новое поверх известного дефекта.
- **Поведение в проде меняется только осознанно.** Рефакторинг сохраняет поведение (snapshot-тесты,
  снимок команд). Изменение поведения названо в ответе. Коммит в `main` сразу уходит в прод.
- Если после чтения кода остаётся несколько равноценных вариантов, спросить пользователя.

## Стек
Python 3.13, discord.py 2.6 (`commands.Bot`, префикс `!` + slash-команды через `bot.tree`),
MongoDB (pymongo `AsyncMongoClient`, БД `sdgame`), paramiko (SSH/SFTP к игровым серверам),
matplotlib, pyvis/networkx. Продакшен в Docker.

## Запуск
- Продакшен: выкатка коммитом в `main` (хук пушит на сервер, там сборка, `pytest` в контейнере и
  `docker compose up -d`; подробно в `docs/SERVER.md`, раздел «Выкатка»). Docker: `docs/DOCKER.md`.
- Локально: `python -m lobby_bot` из корня проекта (там же `.env`); бот стартует в `run()` (`lobby_bot/__main__.py`).
- Объект `bot` (класс `LobbyBot`) создаётся в `lobby_bot/app.py`. Фичи его не импортируют, а используют `self.bot`.
- Импорты ядра только абсолютные: `from lobby_bot.settings import settings`, `from lobby_bot.db import Database`,
  `from lobby_bot.features.elo import service`.
- Не запускать вторую копию с тем же токеном, пока работает продакшен: команды ответят дважды,
  очередь ELO обработается дважды.
- Зависимости: `requirements.txt` (версии закреплены). `py-cord` не использовать: конфликтует с discord.py.

## Конфигурация и секреты
- Все токены, адреса серверов, SSH-пути, ID каналов/ролей/админов и личные ссылки только в `.env`.
  Полный список ключей в `.env.example`. Читать только через `from lobby_bot.settings import settings`
  (`settings.panel_channel_id`), не через `os.getenv`/`load_dotenv`.
- Новый ключ: поле в классе `Settings` (lobby_bot/settings.py, имя = переменная в нижнем регистре, с типом)
  + строка в `.env.example`. Литералы ID и адресов в коде не писать.
- Секреты в `Settings` типа `SecretStr`: значение через `.get_secret_value()` (или `secret_value()`
  для необязательных). Ошибка настроек при старте перечисляет ключи без значений.
- Не читать и не выводить `.env`, `credentials.json`. Секреты в логи не писать.
- Slash-упоминания вида `</srv:ID>` в текстах остаются в коде: ID команд не секрет.

## Тесты
- Запуск: `pip install -r requirements-dev.txt`, затем `pytest` из корня. Реальные `.env`, MongoDB
  и Discord не нужны: `tests/conftest.py` подставляет фейковые значения ключей из `.env.example`
  и mongomock вместо AsyncMongoClient (асинхронная обёртка `tests/async_mongo.py`, `wrap(col)` для репозитория
  в тесте). Подготовка и проверка данных синхронно через `tests/mongo.py` (`mongo.player_ratings_col`,
  `mongo.seasons()`). Новый ключ в `.env.example` сразу попадает в тесты.
- Структура `tests/` повторяет код: `tests/features/<фича>/test_*.py`; фейки фичи в её `conftest.py`.
- `tests/test_startup.py`: смоук старта (задачи, Cogs, persistent-кнопки) и снимок команд
  `tests/commands_snapshot.txt`. При рефакторинге набор команд не должен меняться; если меняешь
  команды намеренно, обнови снимок.
- Snapshot-тесты (`tests/snapshot.py`, эталоны в `snapshots/<модуль теста>.json` фичи) фиксируют поведение,
  перенесённое из старого кода. Рефакторинг эталоны не меняет. Вывод меняется намеренно:
  `UPDATE_SNAPSHOTS=1 pytest <тесты>` и проверить diff эталонов; новый тест пишет эталон тем же способом.
- Предупреждения в тестах = ошибки (`filterwarnings` в `pyproject.toml`): устаревший API чинить, а не глушить.
  Исключение только для предупреждений внутри чужих библиотек, с причиной в комментарии.
- Известный баг из «Известных проблем» покрыт тестом `@pytest.mark.xfail(strict=True)` с ожидаемым поведением:
  после исправления тест начнёт проходить, и пометку надо снять.
- Внешние сервисы (SFTP сайта, EOS API, SSH серверов) в тестах подменяются фейком на уровне клиента
  (paramiko, aiohttp-сессия), а не моками функций самой фичи.
- После каждого изменения прогонять `pytest`. Рефакторишь или меняешь поведение: сначала тест на текущее поведение.

## Линтер и CI
- Ruff (настройки в `pyproject.toml`, длина строки 120): `ruff check .` и `ruff format .` из корня. Перед коммитом
  их запускает pre-commit (`.pre-commit-config.yaml`; один раз `pip install pre-commit` и `pre-commit install`).
- Правило не отключать ради одной строки: длинную строку разбить, исключение (`# noqa`) только с причиной.
- CI (`.github/workflows/ci.yml`): `ruff check`, `ruff format --check`, `pytest` на каждый push в GitHub.
  Выкатка на сервер (`deploy/post-receive`) запускает только `pytest`.

## Документация и сервер
- Документация в `docs/` (`ARCHITECTURE.md`, `DOCKER.md`, `SERVER.md`); в корне только `README.md` и `CLAUDE.md`.
- Всё, что установлено на сервере вне Docker (скрипты, cron), хранится в `deploy/` и описано в
  `docs/SERVER.md`. Изменил на сервере: обнови копию в репозитории.
- Данные (`game_csvs/`, логи) в git не кладутся. `*.sh`, `.githooks/*`, `deploy/post-receive` только с LF
  (`.gitattributes`).
- Каждый коммит в `main` сразу уходит на сервер и выкатывается, если прошёл `pytest` на сервере
  (`.githooks/post-commit`, `deploy/post-receive`). Шаги, которые надо сначала проверить на сервере,
  делать в отдельной ветке.

## Docker
- `Dockerfile`, `docker-compose.yml`, `.dockerignore`; инструкция в `docs/DOCKER.md`.
- Бот в контейнере с `network_mode: host`, MongoDB снаружи (по `MONGO_URL`).
- SSH-ключи, папки CSV и `logs/` подключаются томами; пути внутри контейнера
  задаются в `environment` docker-compose.yml и перекрывают значения из `.env`.
- Новые файлы, которые нужны боту в рантайме и не являются кодом, подключать томом, а не класть в образ.
- В значениях `.env` символ `$` удваивать (`$$`): Compose его интерполирует.

## Фичи (`lobby_bot/features/<имя>/`)
- Фича = папка-пакет. Подключается строкой в `EXTENSIONS` (app.py) через `load_extension`;
  выключить фичу = убрать строку. В модуле `cog.py` функция `async def setup(bot)`.
- Внутри до трёх ролей, лишние не создавать: `cog.py` (Discord: команды, кнопки, задачи, embed'ы),
  `api.py`/`service.py` (внешний API или логика, без discord), `repo.py` (MongoDB). Исключения:
  `views.py` (кнопки, меню, embed'ы) отдельно от `cog.py`, только когда `cog.py` больше ~800 строк;
  `api.py` и `service.py` вместе, когда есть и внешний API, и своя логика (servers: SSH + правила).
- Зависимости передаются в Cog через конструктор (собираются в `setup`). Cog не импортирует `bot`
  из app.py, а использует `self.bot`. Фичи между собой общаются только через service, не через cog;
  по Discord-части только событиями (`self.bot.dispatch`, список событий в `docs/ARCHITECTURE.md`).
- Задачи `@tasks.loop` только в Cogs фич (в `app.py` задач нет): старт в `cog_load`, остановка в
  `cog_unload`, `before_loop` ждёт `wait_until_ready`. Тело задачи в `try/except` с `logger.exception`:
  необработанное исключение навсегда останавливает задачу. Первая итерация выполняется сразу при
  `start()`: не дублировать её ручным вызовом.
- MongoDB: асинхронный `Database` (`lobby_bot/db.py`). Бот создаёт его в `setup_hook` (`bot.db`), фича берёт
  коллекции в `setup()` (`bot.db.players`) и передаёт в свой repo; методы repo `async`. Синхронного клиента нет.
- Тяжёлые синхронные операции (расчёты, paramiko) в задачах через `asyncio.to_thread`.
- Выключаемая фича: флаг `<ИМЯ>_ENABLED: bool = False` в `Settings`, проверка в `cog_load` перед стартом задач.
  Не комментировать код и не убирать фичу из `EXTENSIONS` ради выключения.
- Кнопки и меню, которые должны жить после рестарта, регистрировать через `add_view` / `add_dynamic_items`
  в `setup()` фичи.
- Общий код фич: `lobby_bot/shared/` (права: `permissions.py`; загрузка на сайт: `web_upload.py`).
- Переносить файлы через `git mv`, чтобы сохранить историю.

## Ключевые правила
- Права: все `!`-команды и `[Мод]`-команды только для модераторов: роль `MODERATOR_ROLE_ID` или ID из
  `ADMIN_IDS` (`lobby_bot/shared/permissions.py`: `is_moderator`; для Cog `cog_check = moderator_check`,
  для одной команды `@moderator_only()`). Новая команда без проверки прав только осознанно.
  Отказ в правах отвечает пользователю `LobbyBot.on_command_error` (app.py).
- Сезон: активный документ в `seasons` (`is_active: True`). Получать только через
  `await current_season(seasons)` из `lobby_bot/features/seasons/service.py`, он читает базу при каждом вызове.
  `seasons` (SeasonsRepo) фича собирает в `setup()` через `seasons_repo(bot.db)`; если команда должна работать
  и без базы сезонов, `season_or_first(seasons)` (тогда сезон 1). Не сохранять сезон в константу и не вычислять
  в значении по умолчанию: только `season=None` и внутри `await current_season(...)`. Это проверяет тест.
- Ввод пользователя в `$regex` только через `re.escape`.

## Готово, когда
- Правка соответствует принципам выше; зелёный `pytest` сам по себе этого не доказывает.
- `pytest` из корня зелёный (или в ответе сказано, что не запускался и почему); `ruff check .` и
  `ruff format --check .` без замечаний.
- Изменения команд, Cogs и задач отражены в `tests/commands_snapshot.txt` и `tests/test_startup.py`.
- Окончания строк не сломаны: в `git diff --stat` нет файлов, где изменены все строки.
- Для нетривиальных изменений прошло ревью `code-reviewer`, находки Critical и High исправлены.
- Встреченный долг убран или назван в ответе и в «Известных проблемах».
- CLAUDE.md, `docs/ARCHITECTURE.md` и `.claude/` не противоречат коду: устаревшее удалено, новое добавлено.
- Коммит и пуш только по просьбе пользователя: коммит в `main` сразу уходит в прод.

## Соглашения
- Комментарии на русском, если не сказано иное.
- Логи только через `logger = logging.getLogger(__name__)`, не `print`.
  Внутри `except` для ошибок использовать `logger.exception` (пишет traceback).
- Не делать сетевых запросов и запросов к БД на уровне модуля (при импорте).
- Время для пользователей московское.

## Известные проблемы
- Логи частично в f-строках.
- ID slash-команд в тексте панели (`</srv:...>` и др.) захардкожены: при пересоздании команд ссылки сломаются.
- match_results: матч, где ELO твинка ушло основному, падает с KeyError (у записи основного нет `team`),
  итогов такого матча нет. Перенесено как было; xfail-тест `test_main_account_change_still_sends_results`.
- Модальные окна создают `TextInput(label=...)`: в discord.py 2.6 атрибут `label` у TextInput устарел
  (замена: `discord.ui.Label`). Пока работает; перейти до обновления discord.py.
- ELO: если модератор правит ELO игрока, пока дописывается прерванный расчёт матча, правка затрётся
  (read-modify-write без транзакции). Полностью закроют только транзакции MongoDB (нужен replica set).
